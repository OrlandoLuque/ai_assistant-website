Purpose

Server implementation of the Agent Client Protocol v1 over JSON-RPC 2.0 / stdio. Lets any ACP-conformant editor (Zed, VS Code, JetBrains) embed ai_assistant as a coding agent the same way they embed OpenHands, Goose, Hermes, or Gemini-CLI. The editor launches ai_acp serve as a subprocess, talks over stdin/stdout, and gets streamed responses back through session/update notifications.

Build

cargo build --release --bin ai_acp --features acp

Verbs

ai_acp serve [--provider PROV --model MODEL [--url URL] [--log-dir DIR]]
ai_acp probe <cmd> [args...]
  • serve — runs the ACP server on stdio with AiAssistant as the LLM backend. Persists per-session SLO records (handshake / prompt / first-chunk timings) to ./.ai_assistant/acp_logs/acp_<ts>_<pid>.jsonl. --provider/--model/--url override the defaults; $ACP_MODEL is read if --model is absent.
  • probe — diagnostic. Spawns the given command as an ACP server, runs handshake + one prompt, prints handshake / first-chunk / chunks-per-sec timings.

SLO targets (in-CI)

  • Handshake < 200 ms
  • First chunk < 1 s
  • Sustained throughput ≥ 30 chunks/s

Two unit tests assert the handshake and throughput targets against stub generators — SLOs are validated at compile time, not just monitored in production.

Capabilities advertised

embeddedContext: true. image, audio, mcpCapabilities, and loadSession default off until each is wired through the corresponding subsystem.

Why no agent-client-protocol crate dependency?

The official crate is at 0.11.x and currently undergoing the SACP redesign. Tracking a moving 0.x API is more maintenance than the JSON-RPC envelope itself (~120 lines, hand-rolled). Re-deriving the ~80 schema types is a serde exercise; we save the dep, the version-tracking burden, and any RFD churn.
