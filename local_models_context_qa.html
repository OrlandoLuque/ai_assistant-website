Local Models: Context, Onboarding & Conversation-QA

Why the assistant used to lose context and invent facts — and everything fixed so the shipped binaries auto-detect a model, keep the conversation on track, and are measured by a real conversation-quality harness (V192–V201).

1. Root cause: the num_ctx truncation bug

Every Ollama chat request sent only temperature and never num_ctx, so Ollama fell back to its ~2048-token window and silently truncated the prompt — dropping injected knowledge and earlier turns. Fixed by auto-sizing num_ctx (VRAM-safe ceiling, quantized, capped at the model window). A/B with the same 145 KB knowledge on llama3.1:8b:

RequestAnswer
without num_ctx (old)“no tengo información…” ❌
with num_ctx = 32768490 ✅

Caveat: an over-large num_ctx does not error — it OOM-crashes the Ollama server (observed at 65536 on an 8B). Auto-sizing is deliberately conservative; larger windows are opt-in.

2. “Just works” onboarding

  • Model discovery probed providers sequentially with retries; dead localhost ports stalled the scan. Now concurrent, single-attempt, short-timeout.
  • Detectors missed a running Ollama and scan took 27 s: ureq tries IPv6 ::1 first. Switched local defaults to 127.0.0.1 and parallelized the scan → Ollama detected in ~2.3 s.
  • The shipped binaries lacked the (dependency-free) butler feature → now in full, so auto-detection ships by default.

4. The conversation-QA harness — what each test means

ai_cli qa runs multi-turn scenarios through one assistant (turn N can ask about turn 1) and scores answers with deterministic keyword checks. It is a bare baseline: Conversation mode, no memory/RAG-store/anti-hallucination/quality-gates — so results are honest.

  • context_recall — basic memory across a distraction turn.
  • grounded_price — read a fact from injected knowledge instead of guessing.
  • multi_fact_tracking — hold four facts at once, recall different ones after distractions. (The profession check matches the stem arquitect, not the exact arquitecta — we test recall, not grammatical gender.)
  • multi_fact_hard — six facts, four distraction turns: a harder stress test of raw-context tracking.
  • fact_update — a fact is corrected mid-conversation; the answer must use the latest value.
  • multi_grounded — several prices across turns from a large document (grounding + retrieval + multi-turn).

5. Measured results across local models

Two measurement fixes (V205) changed the picture. An earlier version reported the extreme-quant models failing multi-fact tracking and updates. Re-measuring found two flaws: (1) --url was silently ignored for the llamacpp provider (written to the wrong config field), so every PrismML run hit the same default :8080 server — the per-model rows were all one server. (2) a gender-inflection scoring artifact: the check required arquitecta but the models correctly recalled the profession as the masculine arquitecto. Both fixed — and most of the "wall" was the harness, not the models.

Deterministic (greedy, temperature 0). Full 6-scenario suite, each model on its own endpoint.

Findings. With the two fixes the "multi-fact wall" largely dissolves: the real 1-bit Bonsai-8B is 6/6 unaided, and even the 1-bit Bonsai-4B is 5/6 (only fact_update missing). The mobile Q4 3B is 6/6. The structured fact ledger (--memory) rescues fact_update on Bonsai-4B (5/6 → 6/6): it records personal facts as a latest-wins ledger (color favorito: rojo overwrites azul) and re-injects them, so the weak model reads the current value instead of being confused by raw history (baseline answered ¡7!). LLM extraction (--memory-llm) is only as good as the extractor — a weak model can misread a correction, so the deterministic heuristic stays authoritative and the LLM only adds facts it misses. Recommendation: prefer a Q4 model of 3B+; enable --memory on extreme-quant models for robust fact-correction. This reproduces on mainstream Ollama models — and has a floor (2026-07-24): qwen2.5:1.5b-instruct matches the Bonsai-4B profile (5/6 → 6/6 via both --memory and --memory-llm self-extraction), but llama3.2:1b stays 4/6 even with a 14B extractor — its misses (multi_fact_hard, multi_grounded) are a chat-model capability gap the ledger can't fill, so 3B remains the reliable sweet spot.

6. FreshContext & retrieval (lexical vs semantic)

FreshContext sends only the latest turn to the model. It used to drop the rest, so recall failed. Now it retrieves what the turn needs from the full conversation — the most recent turns verbatim (so a correction is never dropped) plus relevant older turns — and passes all 5 scenarios on 8B and 3B.

Stores & rankers. The default rag.db is SQLite FTS5 (lexical); semantic/vector (LanceDB, embeddings) is an opt-in tier. Ad-hoc --knowledge / FreshContext retrieval defaults to semantic (Ollama nomic-embed-text embeddings, cosine), falling back to lexical when the embedder is unreachable. Semantic is the default because it is strictly better when embeddings are available; lexical is kept as the offline, zero-dependency fallback (--lexical forces it).

Why it matters — a 30 KB doc with “encargada de las finanzas es Carlos Vega” buried, queried with the paraphrase “¿quién gestiona el dinero?” (no shared words):

RankerResult
lexical (--lexical)“no information found” ❌
semantic (default)“Carlos Vega.” ✅

7. Mobile & on-device

What this work established about running the assistant on a phone — kept here so we don't lose the thread for future work.

ClassQ4 sizeRuns onSpeed (flagship)
1–1.5B (llama3.2:1b, qwen2.5:1.5b)~0.7–1.1 GBmost modern phones (6 GB+)~15–30+ tok/s
2–3B (gemma2:2b, llama3.2:3b)~1.6–2.3 GBflagships / 8 GB+ RAM~5–15 tok/s
7B+~4.5 GB+not practical on-device—

3B Q4 is the practical sweet spot — needs ~3–4 GB free RAM and scored 6/6 on the full harness, so a phone-sized model is genuinely capable, not just runnable. On-device runtimes: llama.cpp, MLC-LLM, Google AI Edge, Apple MLX. The whole stack runs server-free: the mobile profile, the in-process embedder (all-MiniLM, ~90 MB) for semantic retrieval, and the structured fact ledger (--memory).

What we improved for a small/local model: grounding stopped inventing prices (the num_ctx fix), paraphrase retrieval works without a server (in-process embedder), fact-correction is robust on weak models (--memory rescues fact_update on the 1-bit 4B), and onboarding works out of the box.

Rescue a cheap local model with a capable remote one (built)

Fact extraction is infrequent and small (one short structured output per turn), so it's cheap to offload to a capable model on a stronger machine — and with the library's distributed / p2p layer that machine can be a home desktop, not the phone. The phone keeps a cheap, private, low-latency chat model; a capable model does the occasional extraction. The local heuristic covers common cases for free, and the heuristic-authoritative merge means a slow/absent/wrong remote extractor can't corrupt a known fact.

Now built: the extractor is a separate, configurable model/endpoint via --extractor-provider / --extractor-url / --extractor-model. It works with every "model on another machine" mechanism — remote Ollama/llama.cpp/vLLM, the OpenAI-compatible ai_proxy mesh gateway, a gpu-sharing/distributed node, or a cloud API — because they are all consumed as an HTTP endpoint and the extractor (SelfChatEnhancer) is a full multi-provider client. Validated: chat on Bonsai-4B (llama.cpp) + extractor on llama3.2:3b (Ollama, a different provider/endpoint) → 6/6.

8. Quick reference

ai_cli scan                        # auto-detect providers
ai_cli models                      # list local models
ai_cli profiles                    # list runtime profiles
ai_cli query --profile mobile --model llama3.2:3b --knowledge big.md "..."
ai_cli qa --model llama3.1:8b      # conversation-quality scenarios
ai_cli qa --fresh-context ...      # run them in FreshContext mode
ai_cli qa --memory ...             # structured fact ledger (heuristic)
ai_cli qa --memory-llm ...         # + LLM fact extraction (same model)
ai_cli qa --memory-llm --extractor-provider ollama --extractor-url http://host:11434 \
          --extractor-model llama3.2:3b ...   # extractor on a different/remote model
ai_cli query --num-ctx 32768 ...   # raise the Ollama window
ai_cli query --lexical ...         # lexical retrieval (default is semantic)
