Anti-Hallucination Guide

Eliminate LLM hallucinations with a configurable 11-step pipeline — 7 strategies, calibrated abstention, faithfulness scoring, and quality gates. No equivalent in LangChain or LlamaIndex.

1. Why This Matters

LLMs hallucinate between 5–20% of their outputs. In medical, legal, and financial applications, a single fabricated fact can cause real harm. Other frameworks offer partial solutions; ai_assistant provides the complete anti-hallucination pipeline in a single crate.

The cost of hallucinations: A hallucinated legal citation can result in court sanctions. A fabricated drug interaction can endanger patients. A wrong financial figure can trigger regulatory action. This is not a nice-to-have — it is a requirement.

2. Quick Start

Get anti-hallucination protection running in three steps.

1

Basic Verification (CLI)

Verify a claim using the built-in CLI with a single command:

bash 
ai_cli verify "Rust was first released in 2015" --strategy mark

The verify subcommand decomposes the input into claims, scores each one, and applies the chosen strategy to ungrounded claims.

2

Full Pipeline with Faithfulness + Quality Gates

Enable the complete pipeline in Rust with faithfulness scoring and quality gates:

Rust 
use ai_assistant::anti_hallucination::*;
use ai_assistant::faithfulness::*;
use ai_assistant::quality_gates::*;

// 1. Configure the anti-hallucination pipeline
let ah_config = AntiHallucinationConfig::production();
let pipeline = AntiHallucinationPipeline::new(ah_config);

// 2. Process an LLM response against source context
let context = "Rust 1.0 was released on May 15, 2015.";
let response = "Rust was first released in 2015. It uses a garbage collector.";
let result = pipeline.process(response, Some(context));

println!("Abstained: {}", result.abstained);
println!("Grounding ratio: {:.0}%", result.grounding_ratio() * 100.0);
println!("Ungrounded claims: {}", result.ungrounded_count);
println!("Processed text:\n{}", result.processed_text);

// 3. Run quality gates
let runner = QualityGateRunner::production_defaults();
let scores = QualityScores {
    faithfulness: Some(0.85),
    confidence: Some(result.overall_confidence),
    grounding_ratio: Some(result.grounding_ratio()),
    ..Default::default()
};
let gate_result = runner.run(&scores);
println!("Quality gates passed: {}", gate_result.passed);
3

Chain-of-Verification (CoVe)

Enable CoVe for multi-step verification with external evidence:

Rust 
use ai_assistant::chain_of_verification::*;

let cove_config = CoVeConfig {
    enabled: true,
    verification_source: VerificationSource::RagThenWeb,
    correction_mode: CorrectionMode::Replace,
    max_claims_to_verify: 10,
    max_llm_calls: 5,
    ..Default::default()
};

// The CoVe pipeline:
//   1. Extracts claims from the draft response
//   2. Generates verification questions for each claim
//   3. Verifies each claim against RAG or web sources
//   4. Corrects or annotates the response

// result.corrected_response contains the verified output
// result.overall_accuracy gives the ratio of supported claims

LLM-backed verification (v0.2.79+)

By default verify_claim() falls back to word-overlap between the claim and the verification context. Attach an LLM callback via with_llm_verifier to get the full CoVe behaviour — the engine sends a Supported / Contradicted / Unsupported prompt to the model and uses its verdict.

Rust 
let cove_engine = ChainOfVerification::new(cove_config)
    .with_llm_verifier(|prompt: &str| -> Option<String> {
        my_llm_client.complete(prompt).ok()
    });

ai_cli verify --cove --knowledge <file> wires this for you and sets verification_source = VerificationSource::Both so that file-sourced contexts are not filtered out. Demo corpora examples/knowledge_earth.txt and examples/knowledge_rust.txt let you try the flow end-to-end:

bash 
ai_cli verify --provider ollama --model "mistral:7b-instruct" \
  --knowledge examples/knowledge_earth.txt \
  --cove --quality-gates \
  "Tell me about Earth"

3. The 7 Ungrounded-Claim Strategies

When the pipeline detects an ungrounded claim, it applies one of seven configurable strategies. Choose the right one for your use case:

StrategyBehaviorBest For
Omit Remove unverified claims entirely from the output Medical, legal — zero tolerance for fabrication
Mark Tag unverified claims with [unverified] marker General use — transparent, lets users judge
Warn Keep claims but emit a warning to the caller Development, logging — non-intrusive monitoring
Footnote Add explanatory footnotes for unverified claims Research, academic — detailed annotation
VerifyThenMark Attempt verification first; mark if still ungrounded Production — best balance of cost and safety
VerifyThenOmit Attempt verification first; remove if still ungrounded High-stakes — maximum safety with verification
Ask Ask the user to confirm or reject each ungrounded claim Interactive — human-in-the-loop validation
Default strategy: Mark. Override it in config or per-request. The mark format is configurable — default is "[unverified] {}" where {} is replaced by the claim text.

4. The 11-Step Pipeline

Every LLM response passes through an orchestrated sequence of checks. Each step is independently configurable and can be enabled or disabled.

Auto-Temperature
Detects factual queries and lowers temperature (default 0.3) before sending to the LLM. Reduces randomness for fact-seeking questions.
LLM Generation
The LLM generates its response with the adjusted (or default) temperature.
Abstention Check
If overall confidence is below abstention_threshold (default 0.3), the pipeline stops and returns an abstention message instead.
Claim Decomposition
Response is decomposed into atomic claims. Two methods: SentenceSplit (zero-cost) or LlmDecomposition (one LLM call, higher precision).
Faithfulness Scoring
Each claim is scored against source context using NLI. Produces per-claim NliVerdict: Entailed, Contradicted, or Neutral.
Grounded Generation Check
Validates that the response is grounded in the provided context and does not introduce unsupported information.
Fact-Check with Search
Claims with NliVerdict::Neutral (no evidence) are fact-checked against external sources (RAG or web search).
Chain-of-Verification (CoVe)
Optional multi-step verification: generates verification questions, checks each against sources, and corrects the response.
Self-Consistency
Parallel/independent check: generates multiple responses and compares them for internal consistency. Flags contradictions.
Apply Ungrounded Strategy
Ungrounded claims are processed using the configured strategy (Omit, Mark, Warn, Footnote, VerifyThenMark, VerifyThenOmit, or Ask).
Quality Gates
Final pass: checks 5 metrics against configurable thresholds. Can Fail (block output), Warn (add warning), or Log (silent).
Cost control: The pipeline respects max_extra_llm_calls (default: 5). Steps that require LLM calls are budgeted and will not exceed this limit, preventing runaway costs.

5. Calibrated Abstention

When the LLM is not confident enough to answer accurately, the pipeline refuses to answer rather than risk a hallucination. This is calibrated abstention — a critical safety mechanism for high-stakes applications.

Rust 
let config = AntiHallucinationConfig {
    enabled: true,
    abstention_enabled: true,
    abstention_threshold: 0.3,  // Abstain if confidence < 30%
    abstention_message: Some(
        "I don't have enough confidence to answer this accurately. \
         Please provide more context or rephrase the question.".into()
    ),
    ..Default::default()
};

let pipeline = AntiHallucinationPipeline::new(config);
let result = pipeline.process(response, context);

if result.abstained {
    println!("Pipeline abstained: {}", result.abstention_reason.unwrap());
    // result.processed_text contains the abstention message
}
Better to say "I don't know" than to hallucinate. In medical and legal applications, a confident-sounding wrong answer is far more dangerous than an honest admission of uncertainty. Calibrated abstention is enabled by default in the production() and strict() presets.

How It Works

The confidence scorer analyzes the response for hedging language ("I think", "probably", "it seems"), certainty patterns, and claim support ratios. If the overall score falls below the threshold, the pipeline returns the abstention message instead of the generated text.

6. Faithfulness Scoring

Evaluates whether each claim in a generated response is supported (entailed) by the source context. Uses Natural Language Inference (NLI) at the claim level.

Two NLI Methods

MethodCostPrecisionHow It Works
WordOverlap Zero (no LLM calls) Moderate Jaccard word overlap between claim and context. Fast but imprecise.
LlmNli 1 LLM call per batch High LLM-based entailment check. Prompts the LLM to classify each claim.

NLI Verdicts

Each claim receives one of three verdicts:

VerdictMeaningNext Action
Entailed Claim is supported by the source context Pass through unchanged
Contradicted Claim contradicts the source context Apply ungrounded strategy immediately
Neutral No evidence found (neither supported nor contradicted) Sent to fact-check with search (step 7)

Code Example

Rust 
use ai_assistant::faithfulness::*;

let config = FaithfulnessConfig {
    decomposition_method: DecompositionMethod::SentenceSplit,
    nli_method: NliMethod::WordOverlap,
    min_faithfulness_score: 0.7,
    word_overlap_entailment_threshold: 0.3,
    word_overlap_contradiction_threshold: 0.05,
    ..Default::default()
};

let scorer = FaithfulnessScorer::new(config);
let context = &["Rust was first released in 2015.", "It is a systems language."];
let response = "Rust was released in 2015 and is a systems programming language.";

let report = scorer.score(response, context);

println!("Overall faithfulness: {:.0}%", report.overall_score * 100.0);
println!("Entailed: {}, Contradicted: {}, Neutral: {}",
    report.entailed_count, report.contradicted_count, report.neutral_count);

for claim in &report.claims {
    println!("  [{}] {} (confidence: {:.2})",
        claim.verdict, claim.claim.text, claim.confidence);
}

7. Chain-of-Verification (CoVe)

A multi-step verification pipeline that generates verification questions for each claim, checks them against external sources, and produces a corrected response.

Verification Sources

SourceDescription
RagOnlyCheck only against the RAG knowledge base
WebSearchOnlyCheck only via web search
RagThenWebTry RAG first, fall back to web search if no evidence
BothCheck both RAG and web search, combine all evidence

Correction Modes

ModeBehavior
ReplaceReplace incorrect claims with corrected text from evidence
AnnotateAdd annotations (e.g., [unverified]) to unverified claims
FootnoteAdd footnotes with full verification details and evidence

CoVe Pipeline Flow

Draft Response
    ↓
Extract Claims → ["Rust uses GC", "Released 2015", ...]
    ↓
Generate Questions → "Does Rust use a garbage collector?"
    ↓
Verify vs Sources → RAG / Web / Both
    ↓
Supported | Contradicted | Unverifiable | Partially Supported
    ↓
Corrected Response (via Replace / Annotate / Footnote)
Rust 
use ai_assistant::chain_of_verification::*;

// Strict: replace contradicted claims, check both RAG and web
let strict = CoVeConfig::strict();
// strict.verification_source == Both
// strict.correction_mode == Replace
// strict.max_llm_calls == 10

// Permissive: annotate only, RAG-only
let permissive = CoVeConfig::permissive();
// permissive.verification_source == RagOnly
// permissive.correction_mode == Annotate
// permissive.max_llm_calls == 3

8. Quality Gates

Quality gates enforce minimum thresholds on 5 metrics. Each gate triggers a configurable action when the metric falls below its threshold — Fail (block), Warn (pass with warning), or Log (silent).

5 Quality Metrics

MetricRangeDescription
Faithfulness0.0 – 1.0Ratio of claims entailed by source context
Confidence0.0 – 1.0Overall confidence score of the response
GroundingRatio0.0 – 1.0Ratio of grounded claims to total claims
ConsistencyScore0.0 – 1.0Self-consistency across multiple generations
CitationCoverage0.0 – 1.0Ratio of claims with source citations

3 Gate Actions

ActionBlocking?Behavior
Fail Yes Block the output entirely — return an error to the caller
Warn No Allow the output but add a warning for the caller
Log No Pass silently, but log the failure for observability

production_defaults() Preset

Rust 
use ai_assistant::quality_gates::*;

// Production defaults: 3 gates
let runner = QualityGateRunner::production_defaults();
// Gate 1: Fail if confidence < 0.3
// Gate 2: Warn if faithfulness < 0.7
// Gate 3: Warn if grounding ratio < 0.5

// Strict: 5 gates including consistency and citations
let strict = QualityGateRunner::strict();
// Fail if confidence < 0.5
// Fail if faithfulness < 0.7
// Fail if grounding < 0.6
// Warn if consistency < 0.5
// Warn if citations < 0.3

// Custom gates
let mut custom = QualityGateRunner::new(vec![
    QualityGate::fail_below("min-faith", QualityMetric::Faithfulness, 0.8),
    QualityGate::warn_below("citations", QualityMetric::CitationCoverage, 0.5),
]);

// Run against scores
let scores = QualityScores {
    faithfulness: Some(0.9),
    confidence: Some(0.7),
    grounding_ratio: Some(0.8),
    consistency_score: Some(0.6),
    citation_coverage: Some(0.4),
};
let result = runner.run(&scores);
println!("Passed: {} | Overall: {:.2}", result.passed, result.overall_score);

CI/CD Integration

Use quality gates in your CI pipeline to prevent low-quality outputs from reaching production:

bash 
# Run quality check via the REST API
curl -s -X POST http://localhost:8090/api/v1/verify/quality-check \
  -H "Content-Type: application/json" \
  -d '{"faithfulness": 0.85, "confidence": 0.7, "grounding_ratio": 0.6}' \
  | jq '.passed'

# In CI: fail the build if quality gates don't pass
RESULT=$(curl -s -X POST http://localhost:8090/api/v1/verify/quality-check \
  -H "Content-Type: application/json" \
  -d '{"faithfulness": 0.85, "confidence": 0.7}')

if [ "$(echo $RESULT | jq -r '.passed')" != "true" ]; then
  echo "Quality gates FAILED"
  echo $RESULT | jq '.failing_gates'
  exit 1
fi

9. Configuration Reference

The anti-hallucination pipeline is configured via TOML (for the server) or Rust structs (for the library). All features are opt-in.

TOML Configuration

config.toml 
[anti_hallucination]
enabled = true
ungrounded_strategy = "mark"           # omit | mark | warn | footnote | verify_then_mark | verify_then_omit | ask
abstention_enabled = true
abstention_threshold = 0.3             # 0.0 - 1.0
confidence_scoring_enabled = true
auto_temperature_enabled = true
factual_query_temperature = 0.3        # Lower = more deterministic
mark_format = "[unverified] {}"        # {} is replaced by claim text
min_confidence_for_output = 0.3
max_extra_llm_calls = 5                # Cost cap

[anti_hallucination.faithfulness]
decomposition_method = "sentence_split" # sentence_split | llm_decomposition
nli_method = "word_overlap"             # word_overlap | llm_nli
min_faithfulness_score = 0.7

[anti_hallucination.cove]
enabled = true
max_claims_to_verify = 10
verification_source = "rag_then_web"    # rag_only | web_search_only | rag_then_web | both
correction_mode = "annotate"            # replace | annotate | footnote
max_llm_calls = 5

11. Security & Cost Protection

The anti-hallucination pipeline includes safeguards against both excessive costs and prompt injection attacks.

Cost Caps

$

Max Extra LLM Calls

The max_extra_llm_calls setting (default: 5) limits how many additional LLM calls the pipeline can make per response. This prevents runaway costs from verification loops. The CoVe pipeline also has its own max_llm_calls budget (default: 5).

Rust 
let config = AntiHallucinationConfig {
    max_extra_llm_calls: 3,  // Tight budget
    ..AntiHallucinationConfig::production()
};

let cove = CoVeConfig {
    max_llm_calls: 5,        // CoVe-specific budget
    max_claims_to_verify: 10, // Hard cap on claims
    ..Default::default()
};

Injection Protection

!

Prompt Injection Resistance

The pipeline's claim decomposition and verification steps are resistant to prompt injection because they process the output of the LLM, not user input directly. Verification questions are generated from extracted claims, not from raw user text. Combined with the security feature's constitutional guardrails, this provides defense-in-depth against adversarial inputs.

Defense in depth: Anti-hallucination is one layer. Combine with security feature (RBAC, PII detection, constitutional guardrails) and eval feature (evaluation suite) for comprehensive production safety.

12. Dataset Benchmarks (V90)

V90 adds a harness that runs the anti-hallucination pipeline against standard community datasets so your numbers are directly comparable with published model cards and prior art. Zero new dependencies, zero vendored data — datasets are fetched on explicit user action and cached locally.

Registered benchmarks

NameSample typeLicenseOpt-in
truthfulqaQA (correct vs. incorrect references)Apache-2.0no
halueval_qaright vs. hallucinated answer pairsMITno
factscoreatomic-claim decomposition (bios)MITno
ragas_wikiqacontextual QA (question + context + answer)Apache-2.0no

Opt-in datasets require --accept-license on download. Cache lives under $CARGO_TARGET_DIR/eval_benchmarks/<loader>/.

CLI

bash 
ai_cli benchmark list
ai_cli benchmark info truthfulqa
ai_cli benchmark download fever --accept-license

ai_cli benchmark run truthfulqa \
    --provider ollama --model mistral:7b-instruct --limit 50

ai_cli benchmark calibrate halueval_qa \
    --provider ollama --model llama3.2 \
    --limit 200 --objective f1 --json

run reports total, correct, accuracy, mean score, per-category breakdown, and wall-clock duration. calibrate adds a post-hoc threshold sweep so you can see where accuracy / F1 peaks for a given model without re-running inference.

HTTP & MCP

Two read-only endpoints surface the loader registry:

http 
GET /benchmarks             → { "total": N, "benchmarks": [...] }
GET /benchmarks/<name>      → metadata, or 404
GET /api/v1/benchmarks...   → same, versioned prefix

MCP exposes two tools (read-only + idempotent):

  • list_benchmarks — enumerate all loaders.
  • get_benchmark(name) — metadata lookup; returns found: false when absent.

Register them with ai_assistant::mcp_protocol::register_benchmark_tools(&mut server).

Programmatic use

Rust 
use ai_assistant::eval_benchmarks::{
    get_loader, run, sweep, default_grid, Objective, RunOptions, report,
};

let loader = get_loader("truthfulqa").unwrap();
let path = loader.download(cache.dir_for(loader.name())?)?;
let samples = loader.load(&path, Some(100))?;

let r = run(loader.name(), &samples, &RunOptions::default(), |prompt| {
    my_llm_call(prompt) // Result<String, String>
});

println!("{}", report::to_text(&r));
let best = sweep(&r, &default_grid(), Objective::F1).best;
println!("Best F1 threshold: {:.2}", best.threshold);
Calibration is post-hoc: the sweep re-partitions existing scores across a 21-point grid (0.00–1.00 step 0.05), so one model run feeds many threshold experiments at zero extra inference cost.
